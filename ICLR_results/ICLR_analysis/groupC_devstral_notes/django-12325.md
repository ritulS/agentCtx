## Mechanisms with evidence
1. Variant choice is a coin-flip made mostly BEFORE compression. Of 16 fallback-final compressed submitters, 12 wrote the fallback at or before the first compression step (e.g. ss r1 28<49, trc r2 28<65, trc-su r2 35<54); 3 wrote it after (su-full r1 62>49, trc-su r1 52>47, su-partial r1 75>51) but had chosen the options.py approach pre-compression. Stated rationale is near-identical in both camps ("prioritize parent_link=True" ss-partial r1 step 25 vs "only add fields with parent_link=True" FC r3 step 29).
2. Old-behavior prior locks in the wrong variant. 36/39 runs wrote or read a test expecting ImproperlyConfigured for a non-parent_link O2O (grep of "should fail|should raise|Correctly failed|assertRaises(ImproperlyConfigured"). The repo's `test_missing_parent_link` was read in 11 runs — none of them resolved; none of the 7 strict-resolved runs read it. Runs that saw the strict fix "fail" their own raise-expectation either reverted to fallback or stalled: tr r3 steps 111-125 ("case 3 is failing – it should raise ImproperlyConfigured"), otrc-tr r1 step 34/37 ("Picking4 should have failed but didn't") — otrc-tr r1 at step 40 reasoned the auto-generated ptr is acceptable and kept the strict fix (resolved); tr r3 never reached that conclusion before the limit.
3. Summaries freeze the prior as an established requirement. ss r1 summary: "4. No parent_link field - correctly raises ImproperlyConfigured" under "All test cases pass"; ss-partial r3 summary: "5. Test no parent_link=True should fail ✓ SUCCESS: Correctly failed with: Add parent_link=True..."; su-full r3 summary: "❌ Discovered a regression: single OneToOneField without parent_link=True now fails". After these summaries no run reconsidered the raise semantics.
4. Post-summary restart (SS/SU-full only). Immediately after compression the agent restarts discovery from scratch: ss r2 step 59 and step 108, ss r3 step 50 ("I'll start by exploring the repository structure..."), su-full r1 step 50. ss r2/r3 spent 50-60 steps re-finding files and re-running repro scripts (ss r3 56-60, 95-110) and never issued `git diff`/submit (gitdiff count: ss r3 = 0, ss r2 = 1). This is the only mechanism unique to compression in this task; it accounts for 3 of the 6 non-bug step-limit runs.
5. Edit-tooling thrash (not compression-specific but amplified by lost file views): heredoc/sed edits with wrong indentation followed by `git checkout` — otrc-su-partial r1 20 cycles (46-123, OTRC clears each result so each cycle starts from the same wrong template), ss-partial r2 14 reverts, trc-ss r2 8 reverts, tr r3 12 debug-print rewrites (71-98). Harness bug (2 runs): otrc-ss-partial r3 and otrc-tr r3 lost the task text at step 0 (trajectory messages[1] = "[tool-result cleared — online-trc — 1405 tok — step 0]"); otrc-tr r3 fabricated a task about a typo in tests/model_inheritance_regress/tests.py; otrc-ss-partial r3 could not find the submit protocol.

## Root cause
This task is a semantics trap: the PR only asks that field order not matter, but the hidden tests additionally flip Django's pre-existing behavior (a non-parent_link OneToOne to the parent must no longer raise, and an auto `*_ptr` must be created), and the repo's own `test_missing_parent_link` plus the ticket's hint patch both point at the "prefer parent_link=True, else fall back to the first O2O" variant that preserves the old raise. Devstral picks between the strict filter (7/7 resolved) and the fallback/options-only variants (0/24) essentially at the first edit, usually before any compression fires (compression at steps 41-65 vs first fallback edit at 25-54 in 12 of 16 cases), so FC's 2/3 vs compressed 5/36 is mostly the base rate of that coin-flip plus a smaller compression-specific loss: SS/SU-full summaries (a) canonicalize the agent's own "no parent_link → must raise" test as a satisfied requirement (ss r1, ss-partial r3, su-full r3) so the variant is never revisited, and (b) trigger from-scratch restarts (ss r2 ×2, ss r3, su-full r1) that burn the remaining budget on rediscovery; the two remaining step-limit failures are OTRC harness bugs, and one (tr r3) has the gold-equivalent base.py fix on disk from step 106 but spends steps 111-125 trying to make its own raise-expecting test pass.
