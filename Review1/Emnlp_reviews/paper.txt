Agentic systems rely on context compression
to execute long-horizon tasks within finite context windows. Existing systems typically adopt
a single compression strategy, such as truncation, summarization, or selective eviction, with
limited understanding of how these choices
affect task success, token usage, and latency
across deployment settings. To better understand the impact of these choices, in this paper,
we present the first systematic characterization
of context compression policies for agentic systems. We organize the compression design
space along three design axes: how context
is compressed, when compression is triggered,
and how aggressively context is compressed.
Using this framework, we evaluate 33 compression policies on SWE-bench Verified across
multiple context budgets and LLMs. We show
that compression policies induce substantially
different tradeoffs between task success, token
usage, and latency, varying by up to 18 percentage points in task success, 1.5× in token
usage, and 1.6× in latency under the same context budget. We further show that different
compression policies solve distinct subsets of
tasks and that the best-performing policy varies
across models and context budgets. Together,
our results show that no single compression policy consistently dominates across deployment
settings, motivating adaptive compression systems instead of fixed global strategies.

Our characterization reveals four key findings
(§3). First, compression policies induce substantially different tradeoffs between task success, token usage, and execution latency, and no single
policy consistently dominates across all three metrics. Second, different compression policies solve
overlapping but distinct subsets of tasks. An oracle that selects the best policy per task improves

The Choices in Context Compression

121

Existing context compression methods (Kang et al.,
2025; Xiao et al., 2025; Gu et al., 2026; Anthropic,
2025; OpenAI, 2025; LangChain, 2025a) combine
multiple design decisions within a single policy,
making it difficult to isolate the impact of individual choices. We represent a context compression
policy using three explicit design axes:
1. how the agent compresses context (primitive
compression mechanism axis),
2. when the agent triggers compression (trigger
axis), and
3. how aggressively the agent compresses context
(depth axis).
A compression policy is fully specified by one
choice along each axis. This formulation provides
a common representation for systematically characterizing context compression behavior across policies. The remainder of this section defines the
design space, and Table 1 summarizes all the compression policies evaluated in Section 3.

2.1

Which compression primitive to use?

142

As agents execute multi-step trajectories, they accumulate tokens across model invocations and tool
interactions (Xiao et al., 2025; Kang et al., 2025).
Once the trajectory exceeds the available context
budget, the agent must compress part of the accumulated context. The compression primitive axis
specifies how compression is performed. Different compression primitives preserve different information. For example, truncation removes portions of the trajectory entirely, while summarization replaces them with a compact generated representation. Thus, the choice of primitive determines which information remains available for subsequent reasoning steps.
We categorize compression primitives into three
families: rule-based, LLM-based, and stacked.
Across these families, we study eight primitives
used in existing agentic systems (Table 1). All
primitives operate only on the accumulated trajectory context; the system prompt and current task
instruction are always preserved verbatim. We describe each family next.
Rule-based. Rule-based primitives compress trajectories using fixed deterministic procedures. We
study two rule-based primitives used in production
agentic systems:
• TR (truncation) removes the oldest messages
from the compressible window until the trajec-

LLM-based. LLM-based primitives compress trajectories by generating shorter representations of

• SS (structured summarization) summarizes the
trajectory using a fixed schema (e.g., files

• SS-p applies SS only to older portions of the

verbatim (Packer et al., 2023).
Stacked. Rule-based primitives are computationally inexpensive but can only compress specific
portions of the trajectory. LLM-based primitives
can compress arbitrary context, but require an additional model invocation at each compression event.
Some production agents combine both approaches to balance these tradeoffs (Packer et al.,
2023; Wang et al., 2025). We therefore also study
stacked primitives, which first apply a rule-based
primitive and invoke an LLM-based primitive only
if the trajectory still exceeds the token budget. We
denote stacked primitives using an addition operator (e.g., TRC+SU).

Q2. Does the choice of compression policy
affect which tasks an agent solves?
So far, we compared compression policies using aggregate resolve rates across all tasks. This comparison implicitly assumes that stronger policies simply
solve a superset of the tasks solved by weaker ones.
We find that this assumption does not hold.
Figure 4 shows the per-task outcomes for all
compression policies. Across the benchmark, 22%
of tasks are solved by every policy, while 25% are
solved by none. For the remaining 53% of tasks,
however, task resolution depends strongly on the
chosen compression policy. An oracle that selects
the best policy per task achieves a 67% resolve rate,
improving by 20 percentage points over the best
individual policy (TRC+SU at 47%).
Different tasks require preserving different
forms of information across long trajectories. Compression policies vary substantially in which information they retain. For example, TR preserves
recent context verbatim while discarding older interactions entirely. SU rewrites the trajectory into
a compact free-form summary, compressing ag6

gressively but potentially removing structural details. SS instead preserves information within a
fixed schema, while step-triggered TRC policies
aggressively remove prior tool outputs throughout
execution. As a result, different policies produce
different trajectory representations, causing different tasks to favor different compression behaviors.
Takeaway #2. Compression policies solve overlapping but distinct subsets of tasks. So, the best compression policy is task-dependent, since policies
preserve different information from the trajectory.

Compression-aware agent design. Existing

Conclusion

We presented the first systematic characterization
of context compression policies for agentic systems.
Our study shows that compression policies induce
substantially different tradeoffs across task success,
token usage, and latency, solve different subsets
of tasks, and vary significantly across models and
context budgets. These findings demonstrate that
no single compression policy consistently dominates across deployment settings. More broadly,
our results motivate adaptive compression systems
that dynamically select compression policies based
on the task, model, and context budget.

Beyond aggregate evaluation. All existing
work (Kang et al., 2025; Xiao et al., 2025; Gu
et al., 2026) evaluates context compression using
aggregate task success under a fixed model and deployment setting. Our characterization shows that
aggregate metrics obscure substantial structure in
compression behavior. Policies with similar aggregate performance often solve different subsets of
tasks, and policy rankings shift across models and

Our study characterizes the cost-resolve trade-off
of context-compression primitives across three
open-weight models, four token budgets, and three
compression depths. While our results give a consistent picture of how primitives behave inside this
regime, the current study has a few limitations.
First, we run all primitives inside a single agent
harness, mini-swe-agent. The harness uses a
trajectory-style tool-use loop with a fixed tool set,
which matches the most common deployment-style
agent design (Jimenez et al., 2024; Wang et al.,
2025). Holding the harness fixed exercises every
primitive under identical conditions and isolates
compression-strategy effects from harness-design
effects. Harnesses that use richer memory architectures, planner-executor splits, or substantially different tool sets may exhibit different compression
behavior, and we have not measured this transfer
directly.
Second, we evaluate on three open-weight codecapable models in the 24–35B range, drawn
from three different lineages (Qwen3, Devstral,
Qwen2.5-Coder). This range balances coverage
across distinct model families with the compute
needed to run every primitive at every budget. The
three lineages let us probe transfer of the trade-off
across qualitatively different agents while keeping the full primitive sweep tractable. We have
not measured frontier closed-source models, much
smaller models, or models trained with explicit
long-context curricula, and the operating points
reported here may not extrapolate to those regimes.
Third, our summarization-based primitives use
the same model as the agent itself to compress
the trajectory. While this keeps the deployment
footprint small and isolates the effect of compression strategy from summarizer-quality differences,
a separately trained or stronger summarizer could
change the ranking of summarization-based primitives, and we have not measured this dimension.

swept along their own axes. Our TRC variants
